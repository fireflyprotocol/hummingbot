# kora-gateway-client
Client edge for Kora spot trading: REST ingress, WebSocket hub, and market-data projections.  **MVP surface.** Day one is Limit + Market orders, GTT only, and three account tabs: holdings, open orders, fills.  Post-MVP endpoints (PnL, account value history, account events, venue stats, all-market tickers) are specified in `docs/superpowers/specs/2026-07-30-spot-gateway-openapi.yaml` and land here when they are built. That file is the design record; this one is the codegen input and the source of truth for what the service serves.  **A fill is not a trade until its state is `settled`.** Matching and settlement are separate events roughly 13-15s apart and settlement can fail. `filledQty` counts settled fills only; a client that treats matched quantity as owned inventory will be wrong for the settlement window and permanently wrong on a bust. No CEX has this property, so it is the largest porting hazard on this venue.  **The WebSocket upgrade endpoints are deliberately not in this document.** `GET /public/v1/ws` (anonymous) and `GET /api/v1/ws` (authenticated) exist and are served, but a WS session is a channel protocol, not a request/response operation — OpenAPI 3.0 cannot express its frames, and generating a handler for it produces the wrong shape, since an upgrade handler must hijack the connection rather than return a response body. They are registered as plain routes outside the generated handler. The frame-level contract is `docs/superpowers/specs/2026-07-31-spot-gateway-websocket-api.md`. `POST /api/v1/ws/ticket` below is an ordinary request and does belong here: browsers cannot set an `Authorization` header on an upgrade, so they mint a ticket and redeem it in-band.
